# Заказные статьи: сторона парсера

Общий контракт — `garden-network/docs/TZ-ggl-orders.md` (принят владельцем 25.09.2026).
Здесь — только то, что делает `gogetlinks-api`. Генерация, публикация и снятие статьи —
на стороне DDL (`ddl-gpbn`).

## Обмен

Через общую таблицу `ddl.ggl_article_order`. HTTP-API нет: парсер и DDL работают на одном
сервере и в одной базе. Схема базы принадлежит DDL — в `schema.sql` этого проекта таблицы нет.

Таблица создана вручную 25.09.2026 (решение владельца: DDL-сторона ещё не реализована, а
парсер уже на сервере). SQL — `docs/sql/ggl_article_order.sql`. Миграция DDL, когда её
напишут, **обязана** быть `CREATE TABLE IF NOT EXISTS`, иначе упадёт на существующей
таблице; поля и ENUM сверить с этим файлом.

Парсер пишет: `task_id`, `domain`, `target_url`, `anchor`, `anchor_inflect`,
`requirements`, `price`, `status='new'`, `notified_at`, `status='cancel'`.
DDL пишет: `status` (`working`/`published`/`cancelled`), `article_url`, `error`, `attempts`.

```
new ──DDL──▶ working ──DDL──▶ published
 │                              │
 └──парсер──▶ cancel ◀──парсер──┘
               │
               └──DDL──▶ cancelled
```

Права: пользователю БД парсера (`ddl`@`localhost`) нужны `SELECT, INSERT, UPDATE` на
`ddl.ggl_article_order`. Проверено 25.09.2026: у него `GRANT ALL PRIVILEGES ON ddl.*`,
делать ничего не надо.

## Что добавлено в парсер

### 1. Передача заказа (обычный часовой прогон)

В `main()`, сразу после уведомления «есть заказ», вызывается
`process_new_article_orders()`. Для каждой **новой** задачи с `title = 'Статья'`
(«Заметка», «Контекстная ссылка», «Ссылка-картинка» не берутся):

- `parse_anchor(description)` разбирает анкор;
- `insert_article_order()` делает `INSERT IGNORE` — повторный прогон заказ не дублирует;
- если анкор не разобрался — заказ **не создаётся**, в ТГ уходит «Есть заказ, анкор не
  распознан» с полным текстом задачи;
- если в задаче несколько анкоров — берётся первый, в ТГ уходит предупреждение.

Уведомление «Новые задачи GoGetLinks» осталось как было.

### 2. Разбор анкора — `parse_anchor()`

Описание заказа начинается строкой `[Анкор] <анкор> (<пометка>)`, дальше идут свободные
требования покупателя.

- `(в любом падеже)` → `anchor_inflect = 1`;
- `(склонять анкор нельзя)` или пометки нет → `anchor_inflect = 0`;
- пробел перед закрывающей скобкой у gogetlinks есть всегда, но не требуется;
- скобки внутри самого анкора пометкой не считаются:
  `Термокамеры (коптильные) для холодного и горячего копчения от ГК «НХЛ»`;
- анкор может быть доменом (`star-tex.ru`) или URL;
- `[Комментарий]` после анкора — на той же строке или на следующей — в анкор не попадает.

Проверено на всех 113 описаниях из `ddl.ggl_tasks` (25.09.2026): разобрались все,
задач с несколькими анкорами в базе нет — ветка на этот случай сделана на будущее.

### 3. Забор результата — `--orders`

Лёгкий режим без Selenium, только БД и Telegram. Подразумевает `--skip-tasks --skip-sites`,
то есть браузер в этом режиме не поднимается даже без флагов.

- `status='published' AND notified_at IS NULL` → «Заказ готов» (сайт, цена, анкор,
  целевой URL, ссылка на статью и на задачу), затем `notified_at = NOW()`.
  Если сообщение не отправилось, `notified_at` не ставится — повтор на следующем тике.
- `status='cancelled' AND notified_at IS NULL` → «Заказ снят», затем `notified_at`.
- `status='working' AND attempts >= 3` **и заказ не обновлялся 30 минут**
  (`ORDER_STUCK_IDLE_MINUTES`) → одно сообщение «Заказ не выходит» с `error`.
  Простой добавлен 26.09.2026 по решению владельца: у DDL три попытки — норма,
  он столько тратит на переделку текста по своим проверкам (живой заказ 25394998:
  «ссылок в тексте 0», «ссылка не в 1–2 абзаце», «ссылок в тексте 2», опубликован
  с четвёртой). Порог 3 из ТЗ сохранён, условие простоя отсекает ложные тревоги.
  Флаг «уже сообщали» хранится на стороне парсера в `logs/order_stuck_notified.json`
  (переопределяется `GGL_ORDER_STUCK_STATE_FILE`) — в таблицу DDL для этого лезть не нужно.

### 4. Отказ — `--cancel-order <task_id>`

Ставит `status='cancel'` и сбрасывает `notified_at`, чтобы потом пришло «Заказ снят».
Тоже без Selenium. Коды возврата: `0` — заказ помечен, `6` — заказа нет или он уже снят,
`4` — ошибка БД. Позже команду заменит кнопка в ТГ (обсуждается при 5+ заказах в день).

## Крон (добавляет владелец вручную)

```cron
*/10 * * * * cd /root/scripts/gogetlinks-api && venv/bin/python gogetlinks_parser.py --orders >> /var/log/gogetlinks_cron.log 2>&1
```

Отдельной строки для передачи заказов не нужно: она работает внутри существующего
часового прогона `0 * * * * ... --skip-sites`.

## Порядок запуска

1. Таблица `ggl_article_order` в базе `ddl` (сделано 25.09.2026 вручную). Без неё парсер
   заказы создать не может: `INSERT` падает, ошибка пишется в лог, остальные стадии не
   страдают.
2. Деплой парсера — `git pull` на сервере (сделано 25.09.2026, `3b70b1c`).
3. Строка крона `--orders` (сделано 25.09.2026, бэкап кронтаба `/root/crontab.bak-20260925-164611`).
4. Осталось за DDL: генерация и публикация заказов. Пока её нет, заказы копятся в `new`,
   парсер по `--orders` штатно ничего не отправляет.
